# Sales synchronization pilot

## Scope

Two independently enabled directions are available. A new confirmed purchase of the last single unit on Allegro withdraws its exact linked Ovoko part with the live Written off status. Reverse synchronization ends the exact Allegro offer only after a new Ovoko-source NEW order, matching part/external reference/publication generation and fresh Sold out state are confirmed. Other Ovoko order states require review: the public schema does not document their lifecycle. Neither direction deletes photos/cars, changes prices, replenishes stock or relists cancellations/returns. This is a limited pilot, not guaranteed protection against simultaneous purchases.

Ordinary and administrator accounts with active access may enable this pilot; suspension or expired access stops writes. It works without an open browser. One account and at most one action are processed per scheduled invocation; direction priority alternates each minute and accounts rotate by oldest attempt. Each enabled direction is normally checked approximately every two minutes for a single account, but provider errors, queues and processing increase delay. Stock greater than one and ambiguous links are not handled automatically.

## Deployment

1. Run `supabase/016_sales_sync.sql`, `supabase/017_inventory_operations.sql`, `supabase/018_reverse_sales_sync.sql` and `supabase/019_sync_ownership_reservations.sql` in order. Migration 019 is required for global physical-account ownership and safe reservation archival. Tables and RPCs are service-only, RLS enabled, with no browser grants. Migration 012 is a prerequisite. No live sale or listing is changed by migration alone.
2. Push the code and wait for Cloudflare Ready. The generated worker config contains `triggers.crons = ["* * * * *"]`; verify the cron under Trigger Events after deployment. This also runs the existing order-mail handler every minute; its existing kill switches and queue remain unchanged.
3. Set `SALES_SYNC_ENABLED=true` in Cloudflare. Existing `ALLEGRO_CLIENT_ID`, `ALLEGRO_CLIENT_SECRET`, `ALLEGRO_ENCRYPTION_KEY`, saved Ovoko connection and service-role DB key must remain correct. `OVOKO_TEST_ENABLED=false` disables this pilot too. No secret is entered in the browser.
4. Open **Synchronizacja** in the left navigation. Enable each direction separately and explicitly. Forward consent probes order access/statuses and saves the current Allegro event cursor. Reverse consent snapshots existing order IDs and eligible single-unit publications; existing orders are excluded. Deployment never silently enables reverse consent.
5. Refresh status after the next trigger. Verify the last check time and no error. The UI does not claim a healthy monitor merely because consent exists. For the first real sale verify both portal states and the action journal. No live provider mutation was performed during development.

Disable consent to stop subsequent actions. `SALES_SYNC_ENABLED=false` is a deployment-level kill switch. Disabling does not reverse an in-flight request or reactivate anything. A changed account, credential fingerprint, expired access or suspension blocks subsequent writes. If work has not resumed for 55 days (Allegro event retention is 60 days), explicit review/re-arming is required.

Migration 019 reserves each physical Allegro seller and Ovoko account to one Wystawiacz owner using unique constraints plus a serialized claim RPC. Both directions share that reservation. Legacy enabled subscriptions and outstanding uncertain writes block another owner even before a reservation has been materialized. Schedulers claim/check ownership before writes. Handover is explicit: disable BOTH directions on the old owner, wait until no active lease remains, resolve preflight/running/submitted/uncertain actions, then use Zwolnij konta. Disabling alone does not release ownership. Release does not copy publication mappings, cursors, reservations or history to another user; deleting/reimporting parts is a separate explicit user operation. Existing conflicting subscriptions fail closed rather than picking an owner arbitrarily.

## Durable Processing

- A five-minute lease plus CAS prevents concurrent schedulers from processing the same account. Previous workers cannot ingest with an expired/replaced lease. Accounts are processed independently.
- Read at most 100 events per tick from the saved cursor. Validate seller, ordering and normalized evidence. The RPC persists sanitized evidence and advances the cursor in one transaction. A full batch means backfill: no portal writes until the queue of events, including cancellations, has been drained.
- Only exact confirmed publication mappings for the current owner, seller, Ovoko account and generation can create an action. The actual item `boughtAt` must be after enable and after the publication timestamp. A delayed READY event cannot apply an old purchase to a newer publication. Missing purchase time or multi-unit lines are not auto-withdrawn.
- BOUGHT/READY duplicates are deduplicated by item, part and publication hash. An order ID missing at BOUGHT waits for a later event. Cancellation moves the action to review, never auto-relist. No buyer details, addresses, names, emails or raw orders are persisted.
- Immediately before a write check fresh order status, exact line item, purchase timestamp and quantity, Allegro current stock zero, exact Ovoko external ID/part ID, current publication hash, active consent/lease/role/account and unchanged saved connections. Reserved/sold/unknown targets are not overwritten.
- An action leaves `queued` via durable CAS. A second CAS to `running` precedes the provider call. Crash/timeout/lost acknowledgments never permit a second write. Readback can confirm `done`; otherwise the row stays uncertain or review. A process abandoned at preflight is also conservative (read-only recovery, not automatic replay).
- Re-arming creates a new subscription epoch but does not erase previous action tombstones. Same physical part, generation and purchase cannot be blindly retried by toggling the switch.

## Verification

Reverse polling overlaps calendar days rather than inventing a timezone for Ovoko's naive order_date. A gap exceeding seven days requires review/re-arming; truncated order reads still fail closed. Migration 022 removes the initial-watch restriction and 499/2000 inventory caps: all current exact mappings for the owner and physical accounts are eligible, including older and newly added pairs. Existing baseline orders remain excluded and consent/history are not reset. See reverse-sync-all-links-022.md for deployment and scope counts. Durable per-generation locks precede deterministic END commands; timeout or lost acknowledgments permit readback only, never blind replay. Multiple orders for one generation require review. No buyer data is persisted.

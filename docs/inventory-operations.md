# Inventory operations

Apply migrations 017 and 019 after the existing publication/withdrawal migrations. Keep INVENTORY_WITHDRAW_ENABLED=true for mutations. No migration alone changes a portal. Private reservation notes use a service-only RLS table; browser clients cannot query it directly. The owning account needs active access (admin, free, paid, eligible trial, or billing unenforced); suspension always denies it. Ordinary accounts do not gain administrator rights. API requests remain authenticated, same-origin and bounded; scheduled writes repeat access checks.

Inventory uses one channel selector and Active / Ended / Sold tabs. Manual ending is not proof of a sale. Allegro sold classification requires sold stock plus zero remaining stock; Ovoko uses the live Sold out dictionary. All selected-channel active states take precedence over ended states; sold has priority. Unknown/partial reads are never invented as sales.

Checkbox selection supports bulk transfer, withdrawal and reservation. Opening a dialog makes no portal writes. Withdrawal chooses Allegro, Ovoko or both with separate durable per-target results, never an atomic success claim. Reservations freeze currently active single-unit stock, record customer, agreed per-part price, deposit, currency, due date and comment, then END Allegro and mark Ovoko Written off. Native Reserved is not used to infer ownership of a reservation. Existing third-party integrations can independently propagate changes and must be reconciled.

Each operation has a request hash and durable execution/target locks. Prepared plans expire after 15 minutes. Repeated confirmation cannot replay uncertain writes. Readback is safe; timeouts remain uncertain until observed state confirms them. Never erase journals to force a retry. A never-started reservation plan may be cancelled without provider writes.

Zarezerwowane lists this application's own open reservations. Expiry highlights red but does not reactivate anything. Restore requires fresh ownership, publication/account binding, unchanged sold counter when known, one remaining unit, and explicit confirmation of physical availability. It ACTIVATEs the same original Allegro offer and returns Ovoko to its original in-stock status, never recreates listings or increases stock. Only one durable restore operation exists per reservation; uncertain restores allow readback, not replay. The parent closes only when all requested legs are confirmed. No arbitrary sold/restocked listing is automatically revived.

Part-number preparation keeps the observed hyphenated spelling as primary and its compact equivalent in the optional field. Server validation corrects older clients that submit only the compact equivalent; fitment lookup still uses compact full numbers. It never invents hyphen positions for an unknown spelling.

Parts share a reservation via a UUID in private reservation JSON, never by customer name alone. Selecting an existing open, unexpired reservation copies its customer, deadline, currency and comment server-side after ownership checks; price and deposit remain per part. Existing reservations without a group ID use their own operation ID. Removing a settled reservation archives only the local record, not portal parts/history and not relisting. Migration 019 serializes archive/restore plan creation on the parent row and cancels an unstarted restore; started/uncertain restores prevent archival. Restoration still requires explicit physical-availability confirmation.

Search matches every whitespace-separated token anywhere in title, codes and IDs, regardless of order/case/accents/hyphens. Sorting supports both prices, names and increasing/decreasing IDs within each portal (IDs are not fabricated timestamps and do not describe relisting dates). Unknown prices are last. Price values are not currency-converted; Ovoko currency remains unverified.

The read-only list has an owner-ID-scoped IndexedDB cache with a five-minute TTL. Navigation verifies login/access, current seller and Ovoko connection before reuse; explicit refresh/mutation completion bypasses and clears it. First pages are displayed progressively, filtering/sorting is memoized. No tokens or reservation customer notes enter this cache. This is NOT a server-side full-text index: first downloads remain provider-rate-limited, batches remain bounded at 2000 records per provider, and search/filter/sort only cover loaded rows. It does not promise instantaneous first-time ingestion or complete search over 40,000 remote records. Browser tests exercise 40,000 synthetic cached rows across real navigation, not provider download throughput. IndexedDB can be cleared by the browser and is local profile data, not encrypted storage.

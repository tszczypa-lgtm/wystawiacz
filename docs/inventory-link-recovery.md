# Recovering publication links

Apply migration 020 after 012 and 016-019. This is a registry-repair feature, not a database backup and not an importer. It is available to the owning account with active access in Synchronizacja > Odzyskaj powiazania po awarii. Both stored portal connections are required. No new environment flag and no provider write permission are introduced.

## Workflow

1. Discover candidates from Ovoko V2 parts in ascending-ID pages of 100, or supply a known Allegro offer ID and Ovoko part ID. Discovery performs provider reads only. It accepts exactly `tymo:<current Allegro seller ID>:<offer ID>`. Untagged records, foreign sellers, arbitrary OE codes and titles cannot establish a link. The discovery list is not an assertion of global uniqueness or completeness; confirmation re-queries the exact external ID. The UI exposes next-page scanning, not an automatic whole-catalog operation. Each selected batch is limited to 10.
2. Before preparing a repair, disable both synchronization directions and resolve started/uncertain writes. Fresh reads must find exactly one Ovoko part for that external ID, with the expected part ID, and exactly one seller-owned Allegro offer. A missing counterpart, duplicate ID, altered identifier or read error blocks the repair. Active/sold/ended status does not establish ownership and never authorizes a provider mutation here.
3. Check selected candidates. The server prepares a five-minute service-only plan, bound to owner, physical accounts, client ID, credentials and pair IDs. This does not insert a publication mapping. Existing identical, confirmed own mappings are reported without modification. Foreign records, sending/uncertain records, conflicting part mappings and old action journals are never overwritten. The existing publication-recovery feature remains responsible for uncertain attempts.
4. Explicitly confirm the reviewed plans. Both portal proofs, account access, connection binding and paused synchronization are checked again. The SQL transaction checks physical-account ownership and synchronization leases/actions, inserts only a missing journal row with origin=recovered and a fresh generation hash, and records the plan as applied. A crash rolls back both or neither. Lost acknowledgment is resolved by refreshing saved plans; repeated confirmation does not insert again. No portal publication, withdrawal, stock, price or photo operation occurs.
5. Pending plans block synchronization enablement and physical-account release using the same advisory-lock domain as ownership claims. Cancel or apply them, or let their five-minute validity expire. Enabling in another tab cannot bypass the DB interlock. Expired/cancelled plans cannot be applied. Recovery never enables monitoring: explicitly arm each direction from now after inspecting the repaired links. It does not recreate event cursors or replay historical sales.

## Boundaries

- Lost reservation notes, sales history, uncertain-write evidence, provider credentials, encryption keys and deleted photos are NOT reconstructed from a part external ID. Auth/application migrations, valid connections and actual portal listings must still exist. Restore a real database backup for lost history.
- An external identifier is an association marker, not a cryptographic certificate of a physical item. Someone with access to the vendor account can edit it. Exact current-account validation, conflict detection and human confirmation reduce this risk; they do not prove which physical item was photographed.
- This does not transfer another user's journal to the current user. Use a separately audited ownership handover rather than bypassing conflicts. Account release alone never copies records.
- Provider state may change after the last read. Synchronization/publishing continue to require their own fresh proofs and durable locks. The recovery registry is not proof that a part is currently available.
- New records are explicitly marked recovered. Their timestamps describe reconstruction, not the original publication date. Historical events must not be interpreted as new purchases on the basis of that timestamp.
- There is no automatic assertion that the whole database or all 40,000 parts were recovered. Discovery is bounded and paged; plans/history are separate from actual live provider state.

## Verification

`test-link-recovery.mjs` uses provider/DB fixtures for exact matching, ownership, conflicts, uncertain journals, expiry, connection/access changes, missing-journal-only insertions, duplicate confirmation, DB acknowledgment loss and absence of provider writes. `test-link-recovery-sql.mjs` executes migrations and the actual repair/enable/release interlocks on isolated PostgreSQL/WASM; it does not simulate multiple Supabase database connections. `test-link-recovery-browser.mjs` checks explicit discovery, review, confirmation and readback without any publish/withdraw/enable request. `test-sales-sync-worker.mjs --production` checks the actual compiled protected endpoint in workerd. No production database or portal mutation was used during development.

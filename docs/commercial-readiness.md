# Synchronization readiness review

Reviewed 2026-11-24 against repository source and current primary documentation. This is an engineering readiness assessment, NOT a production audit, uptime certificate or legal opinion. No vendor dashboards, actual subscribed plans, live billing, backups or production sale outcomes were verified in this task.

## Verdict

NO-GO for marketing a broadly available, unattended, immediate two-way stock-protection service. The implementation has useful fail-closed safeguards and meaningful local tests, but capacity, lifecycle coverage and operational recovery still have release blockers. A small explicitly supervised pilot is a possible next release stage only after the live validation gates below; charging for that pilot requires separate commercial/legal review and transparent limits. Local tests alone do not establish suitability for paid production use.

## Existing safeguards

- Per-user authorization and connection isolation, encrypted saved credentials, same-origin authenticated mutation routes, service-only database journals/RLS and current access checks before writes.
- Physical Allegro/Ovoko account ownership shared by both directions; explicit consents, kill switches, leases, per-action CAS and deterministic Allegro command IDs.
- Exact publication generation, seller, part and external-ID proof; current source/target reads; no OE/title-only joining and no inference of sale from absence/manual withdrawal.
- Uncertain provider writes are not replayed. Readback and manual review are conservative; cancellations/returns never blindly relist stock. Recovery plans never alter portal listings or enable synchronization.
- Source/unit/browser tests, actual PostgreSQL/WASM migration tests and actual compiled workerd routing checks. These do not validate real provider transitions, production cron delivery or multi-connection DB races.

## Release blockers

1. **Throughput and lag.** `build/sites-worker.ts` processes at most one subscription and one action per scheduled invocation, alternating directions. The cron is once per minute. With N active accounts in each direction, a nominal per-account revisit is around 2N minutes before backlog/provider delays, not a fixed two minutes for every customer. Move to durable independently bounded per-account jobs/queues, retries for reads, explicit queue-age metrics and capacity tests. Never increase concurrency without preserving ordering, cancellation ingestion and write locks.
2. **Supported scope.** Forward processing is limited to a confirmed last single unit. Reverse processing supports documented NEW Ovoko orders plus fresh Sold out/exact linkage, not all order lifecycle states. Reverse initial arming refuses 500 or more mappings and catalogs over 2000 items. The read-only list loads bounded batches and has a browser cache, not a server-side index over 40,000 remote records. These limits are not a large-catalog commercial offering.
3. **Operational monitoring.** Status fields and console logs are not an independently verified watchdog. Require alerts for missing scheduled checks, oldest queued action, authorization failures, lease stalls, uncertain writes and a known double-sale signal. Add operator-visible resolution/runbooks, escalation ownership and off-switch drills. Verify that retained provider errors/logs do not expose customer data or credentials. In-memory request throttles are per isolate, not a demonstrated distributed tenant budget.
4. **Recovery gaps.** An uncertain preflight/write can deliberately remain blocked; disabled/re-armed epochs do not provide a complete operator-facing reconciliation workflow for every old journal. Resolve this without deleting locks or inventing a successful write. Test account rotation, redeploys, overlapping crons, connection renewal, midnight/date boundaries, gaps and provider cancellation/return transitions.
5. **Actual hosting configuration.** The repo configures a cron but does not prove it is installed, firing, correctly billed or within CPU/subrequest limits. Dashboard variables are preserved, so source cannot establish the deployed plan/budgets. Check actual scheduled invocation metrics and error outcomes under realistic load. Cloudflare documents materially different Free/Paid CPU/subrequest limits; verify the minute-cron budget rather than assuming a reputable provider makes the application reliable. [Cloudflare limits](https://developers.cloudflare.com/workers/platform/limits/), [Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [logs and monitors](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).
6. **Backups and restore drills.** Confirm an actual backup schedule/retention and test restoration to an isolated project, not production. Define accepted data loss (RPO) and recovery duration (RTO), protect encryption keys separately, and retain an off-site copy. Supabase documents daily backups for Pro/Team/Enterprise and recommends independent exports for Free. Database backups do not contain Storage objects, so photos/files require a separate plan if hosted there. Link reconstruction cannot replace history or object backups. [Supabase backups](https://supabase.com/docs/guides/platform/backups).
7. **Commercial and privacy approval.** Verify current API terms, the Allegro application registration/compliance status, Ovoko integration authorization, customer consent, customer-facing scope, support, billing/refunds and privacy/data-processing documents with appropriate professional review. Presence of policy/billing code is not proof of contractual approval or lawful commercial operation. No legal permission is asserted here. [Allegro API rules](https://developer.allegro.pl/rules).

## Live pilot gates

- Independently back up before migrations, run migrations on staging, verify roles/constraints with parallel database clients, test rollback/redeployment and restore a staging backup successfully.
- Use explicitly selected controlled test listings, not unrelated stock. Observe real purchases in BOTH directions, cancellations/returns, zero/multi-unit stock, duplicate markers, withdrawn/deleted counterparts and connection/access revocation. Record provider timestamps, poll/command/readback timestamps, maximum observed lag and operator response.
- Exercise timeout/lost-response/restart scenarios with no duplicated provider mutation, plus unavailable API/DB, exhausted budgets, missing cron ticks, backlog and stale browser caches. Verify recovery does not reactivate either channel and that a complete outage cannot display an indefinitely healthy monitor.
- Define and measure supported tenant/catalog/order limits and target lag before advertising them. Do not claim zero overselling: independent marketplaces can accept purchases before either has observed the other.
- Only after the blockers are addressed and gates evidenced should the production support/billing decision be made. A small supervised pilot is not evidence that arbitrary tenant counts or catalogs are safe.
